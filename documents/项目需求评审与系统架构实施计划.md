# 法律AI类案检索系统：需求评审、代码Review与实施计划

版本：v1.0  
日期：2026-04-01  
范围：基于 documents 目录需求文档 + 当前仓库代码（deli_api 包）

---

## 1. 执行摘要

当前仓库已经完成了一个可用的 `deli_api` 检索集成SDK（案例检索/法规检索 + LangChain 检索器 + 工具化封装），适合作为后续系统的“检索基础层”。

但按需求文档（裁判规则库）目标衡量，项目尚未进入“业务系统实现阶段”：
- 尚无应用层（FastAPI/Streamlit/Gradio）
- 尚无 GPT-5.3-codex 结构化提取链路
- 尚无 Excel/Word 报告生成模块
- 尚无测试体系与评测基线

结论：项目处于“底层能力完成、业务层未落地”的状态。建议采用“分层架构 + 两阶段交付”：
1) 先交付 MVP（可运行的检索+结构化+导出）
2) 再做专业增强（准确率、可视化、模板扩展、性能与鲁棒性）

---

## 2. 需求理解与范围划分

## 2.1 需求目标（来自文档）

核心目标一致：
- 自然语言输入案情，完成类案检索
- 输出两类产物：Excel 检索表 + Word 检索报告
- 关键能力：
  - 从“法院认为”提炼“主要原因”
  - 自动分类“关键裁判结论”（权利类/金额类/行为类）
- 法规时效性提示 + 数据来源可追溯 + 合规提示

## 2.2 功能边界建议

建议将系统拆为四层，避免 SDK 与业务逻辑耦合：
- 接入层：Web UI / API
- 编排层：任务流、Prompt、重试、缓存、审计
- 领域层：检索后处理、结构化抽取、规则归纳、报告生成
- 基础设施层：deli_api、LLM 网关、文件存储、日志监控

## 3. 当前代码基线评估（Code Review）

## 3.1 已完成能力（优点）

1. SDK 分层清晰
- `DeliLegalClient` 负责上游请求与标准化
- `CaseRetriever`/`LawRetriever` 对接 LangChain
- `create_search_cases_tool`/`create_search_laws_tool` 可供Agent调用

2. 异常体系完整
- 已定义统一异常基类与细分异常，便于上层分类处理

3. 数据模型可用
- `LegalHit` 结构化字段完整，支持转 `Document`

4. 示例可运行
- `examples/basic_usage.py` 已验证基础链路连通

## 3.2 主要问题与风险（按优先级）

### P0（必须优先修复）

1. 工具默认参数 `defaults` 失效风险
- 现象：工具函数参数均有非空默认值，合并策略会覆盖 `defaults`，导致 README 示例语义不成立。
- 影响：Agent 调用工具时，预设参数（如 `page_size=3`）可能不起作用，影响召回规模与稳定性。
- 建议：将可配置参数改为 `None` 默认，并在合并后回填默认值，或显式标记“用户是否传参”。

### P1（应在MVP阶段修复）

2. 客户端生命周期管理存在副作用
- 现象：外部注入 `httpx.Client` 时，`close()` 仍会无条件关闭。
- 影响：若上层共享连接池，会被提前关闭。
- 建议：增加 `_owns_client` 标志，仅关闭内部创建的 client。

3. 环境变量解析未统一异常语义
- 现象：`DELILEGAL_TIMEOUT` 解析失败会抛原生 `ValueError`。
- 影响：上层无法统一捕获 `DeliLegalConfigError`。
- 建议：捕获转换异常并抛 `DeliLegalConfigError`。

### P2（后续优化）

4. 冒烟脚本与README描述不完全一致
- 文档声称包含“客户端直调 + 检索器 + 工具”，脚本主要演示后两者。
- 建议：补齐客户端直调演示，降低认知偏差。

5. 缺少自动化测试
- 当前无单测/集成测试目录。
- 建议：尽快补最小测试集（参数合并、异常分流、响应解析）。

## 3.3 与需求文档的差距（Gap）

当前缺失的关键模块：
- LLM 结构化提取模块（主要原因/关键裁判结论）
- Excel 生成模块（固定模板 + 动态字段）
- Word 报告生成模块（规则归纳 + 可视化）
- API 服务层与前端交互层
- 评测体系（准确率、性能、回归）

## 4. 建议系统架构（面向比赛与可落地）

## 4.1 逻辑架构

1. Presentation 层
- Streamlit（比赛演示优先）或 Gradio
- 功能：案情输入、过滤项、任务提交、结果下载

2. Application 层（FastAPI）
- `/search`：检索并返回结构化中间结果
- `/generate/excel`：生成并返回 Excel
- `/generate/report`：生成并返回 Word/PDF
- `/task/{id}`：查看任务进度

3. Domain 层
- Query理解与过滤器标准化
- 类案召回与去重
- 裁判理由提炼
- 关键结论三分类抽取
- 报告聚合与可视化数据准备

4. Infrastructure 层
- `deli_api`：外部检索能力
- LLM Client（GPT-5.3-codex）
- 缓存（本地文件/Redis）
- 可观测性（日志、trace、指标）

## 4.2 推荐流程（E2E）

1. 用户输入案情 + 可选过滤器
2. Query 重写与扩展（同义词、法言法语补全）
3. `queryListCase` 召回 TopK
4. LLM 对每条案例提取：
- 主要原因（精简）
- 关键裁判结论（权利/金额/行为）
5. 汇总统计：支持比例、金额分布、行为义务分布
6. 可选调用 `queryListLaw` 补法规时效性提示
7. 生成 Excel + Word，附引用与免责声明

## 5. 技术实现路径（分阶段）

## 5.1 Phase A：MVP（2~3周）

目标：可演示、可下载、可复现。

范围：
- FastAPI 最小接口 + Streamlit 页面
- 案例检索（deli_api）
- GPT-5.3-codex 抽取两项核心字段
- 导出最小版 Excel（6列）
- 导出基础 Word 报告（无复杂图表）

验收：
- 输入案情后 30 秒内完成输出（10例以内）
- 能稳定生成 Excel/Word

## 5.2 Phase B：专业增强（2~4周）

目标：提高法律可用性与评审表现。

范围：
- 个性化字段模板（按案由）
- 三类结论分类准确率优化
- 引入法规时效性提示
- 报告图表（判赔比例/行为义务分布）
- 增加缓存与重试策略

验收：
- 分类准确率目标 >= 95%（人工评审集）
- 失败重试后成功率显著提升

## 5.3 Phase C：工程化收尾（1~2周）

目标：稳定、可交付、可展示。

范围：
- 自动化测试与回归报告
- 日志与监控
- 配置分环境（dev/test/prod）
- 演示脚本、操作手册、答辩材料整理

## 7. 测试与质量保障策略

## 7.1 测试分层

1. 单元测试
- 参数合并逻辑
- 异常分流逻辑
- 提取结果 schema 校验

2. 集成测试
- deli_api 真机连通
- LLM 输出结构化约束
- Excel/Word 生成链路

3. 端到端测试
- 输入自然语言案情，验证完整导出与字段正确率

## 7.2 关键指标

- 准确性：关键结论分类正确率 >= 95%
- 性能：10案例场景端到端 <= 30秒
- 稳定性：异常覆盖率 100%，关键链路可重试
- 可追溯：每条结论都可回链到案例 `citation`

---

## 8. 风险清单与应对

1. 法律语义抽取不稳定
- 应对：结构化 JSON schema + few-shot + 后处理规则兜底

2. 上游接口波动
- 应对：重试、熔断、缓存、降级提示

3. 报告生成耗时超标
- 应对：并行处理、分页召回、异步任务队列

4. 合规风险
- 应对：全链路标注来源与时效性，固定免责声明模板
