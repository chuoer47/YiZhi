# 二、项目解决方案

## 1. 项目技术实现方案

### 1.1 总体技术路线与目标
本项目采用“法律检索接口 + 大模型结构化抽取 + 自动化文档生成”的三段式技术路线，目标不是仅返回检索结果，而是将检索结果转化为可交付、可复核、可复用的结构化成果。系统从自然语言问题出发，完成查询增强、候选案例召回、关键字段抽取、法律依据补全、统计汇总和文档输出，最终生成 Excel 类案检索表与 Word 检索报告。该路线解决的是法律场景中的“从信息到结论”效率问题，而非简单的信息抓取问题。

### 1.2 架构设计与关键技术选型
系统采用分层架构。接入层由 FastAPI 和 Streamlit 组成：FastAPI 负责标准化 HTTP 接口与参数校验，Streamlit 负责任务发起、结果预览与文件下载。编排层由 `workflow` 模块承担，使用 Python `asyncio` 组织并发处理，使多案例抽取可以并行执行。数据接入层由 `deli_api` 统一封装对得理开放平台的调用细节，避免业务层直接依赖上游接口格式。生成层使用 `openpyxl` 和 `python-docx` 做模板化导出，保证结果具备文档交付标准。  
在模型编排上，项目使用 LangChain 与 Pydantic 结合的方式：LangChain 负责调用与链路组织，Pydantic 负责输出结构约束。该组合的核心价值是把模型输出从“自然语言段落”变为“可计算对象”，让后续统计、导出和报告拼装具备工程确定性。

### 1.3 检索与抽取工作流详解
当用户提交 query 后，系统首先进入查询增强阶段。模型根据原始问题生成多条“法律检索友好”的改写语句，默认改写数量由 `REWRITE_QUERY_COUNT` 控制（当前为 3）。系统会对改写结果进行约束校验，要求改写语句彼此不同且不与原句重复。  
随后进入案例召回阶段，系统通过 `queryListCase` 分页拉取候选数据。分页规模由 `PAGE_SIZE` 控制（当前为 5），并采用“先召回、再去重”的策略，去重键以案号规范化结果为核心（统一括号样式、移除空格）。该策略可以减少同案重复文书造成的样本污染。  
在字段抽取阶段，系统针对每条案例内容执行结构化抽取，目标字段包括案由、法院审理程序、法院层级、法院认为（精简后）、裁判结果、主要原因以及关键裁判结论三分类。抽取结果直接映射到 Pydantic 模型，避免自由文本解析带来的不稳定。  
完成案例抽取后，系统进入法律依据补全阶段。模型先为每条案例生成多条法规检索语句，再调用 `queryListLaw` 获取法律条文候选，并提取“法律名称 + 条文”作为最终法律依据。为了控制长度与可读性，当前逻辑默认取前 2 条有效法规项并用全角分号拼接。若未命中有效法规，则给出“未检索到明确法律条文”作为兜底值。  
最后，系统将所有字段组装为统一行结构，作为 Excel 和 Word 两条产线的共同输入，保证两个输出渠道的数据一致性。

### 1.4 并发模型、性能与稳定性机制
系统在案例处理阶段采用异步并发模型。每条案例的抽取与法规补全过程在协程中执行，并通过 `Semaphore` 控制并发上限（`MAX_CONCURRENCY` 当前为 5），从而在吞吐与稳定性之间取得平衡。网络请求层使用 `httpx`，并在 `deli_api` 中建立了分层异常体系，能够区分 HTTP 状态异常、请求异常、响应解码异常和业务异常。  
从稳定性角度看，当前链路已经具备基本参数校验和上游异常分类，但在“模型返回空结构”场景下仍需要进一步加强兜底策略（例如结果空值判定、重试与降级），以避免单条样本异常影响整批任务。

### 1.5 Excel 与 Word 生成机制详解
Excel 导出并非简单写表，而是按法律实务使用习惯组织列结构，包含审理法院、案号、案由、法院审理程序、法院层级、法院认为（精简后）、裁判结果、主要原因、关键裁判结论三分类以及法律依据。导出时会统一设置表头加粗、自动换行和列宽，提升审阅效率。  
Word 导出采用分节模板化生成。系统先由模型产出报告主体内容（标题、案情概述、检索方法、核心裁判要旨、结果分析等），再将结构化内容映射到固定章节；随后根据附件筛选结果插入原文案例，形成“结论 + 证据原文”的完整报告。文档层面采用统一字体、段落缩进、行距和表格样式，确保输出接近正式法律文书阅读体验。

### 1.6 环境配置与依赖
项目通过 `.env` 管理外部能力接入参数。大模型接入当前使用腾讯混元大模型 API，代码中使用 `LLM_*` 作为统一配置键名，保证与现有实现兼容。法律检索接口参数由 `DELILEGAL_*` 管理，支持 base_url 和超时配置，便于在不同部署环境下迁移。

#### 1.6.1 环境变量（与代码一致）
- `DELILEGAL_APP_ID`
- `DELILEGAL_SECRET`
- `DELILEGAL_BASE_URL`
- `DELILEGAL_TIMEOUT`
- `LLM_API_KEY`
- `LLM_BASE_URL`
- `LLM_MODEL`

#### 1.6.2 关键依赖
- Web 服务与路由：`fastapi`、`uvicorn`
- 网络请求与配置：`httpx`、`python-dotenv`
- 模型编排与结构化输出：`langchain-core`、`langchain-openai`、`pydantic`
- 文档生成：`openpyxl`、`python-docx`
- 前端展示：`streamlit`

## 2. AI 工具使用说明（工作流与 Prompt）

### 2.1 AI 在本项目中的职责分工
AI 主要承担五类任务：查询改写、案例字段抽取、法律检索查询改写、报告正文生成、附件案例筛选。每类任务对应独立 Prompt 与独立结构模型，避免单个 Prompt 负担过重。与通用聊天不同，本项目的 AI 调用强调“强约束输出”：每次调用都附带 schema 描述和业务上下文，要求模型输出可直接进入程序逻辑。

### 2.2 工作流执行链路（按任务阶段）
Excel 工作流中，模型先完成 query 改写，再对案例进行字段抽取，然后改写法规检索语句以补全法律依据；Word 工作流在复用 Excel 样本的基础上继续生成报告正文，并从候选案例中筛选附件。  
两条工作流共享同一批结构化样本数据，减少“Excel 与 Word 内容不一致”风险，同时降低重复计算成本。对于实际运行，建议先执行 Excel 工作流作为质量闸门，确认抽取稳定后再执行 Word 报告生成。

### 2.3 Prompt 工程方法与输入组织
Prompt 被拆分为 system 与 human 两类模板。system 模板负责角色边界、输出风格和禁止项，human 模板负责注入具体上下文，例如 query、案例摘要、候选列表和 schema 文本。模板通过 `render_prompt` 动态渲染后发送给模型。  
这种“模板化 + 参数化”方式有两个直接收益：第一，业务同学可以在不改代码的情况下调整表达策略；第二，不同任务可以复用同一套渲染机制，降低维护复杂度。

#### 2.3.1 Prompt 目录
- `src/workflow/prompts/excel/`
- `src/workflow/prompts/word/`

#### 2.3.2 Prompt 与任务映射
- 查询改写：`rewrite_queries_system.txt`、`rewrite_queries_human.txt`
- 字段抽取：`extract_case_fields_system.txt`、`extract_case_fields_human.txt`
- 法律查询改写：`rewrite_law_queries_system.txt`、`rewrite_law_queries_human.txt`
- 报告生成：`writer_system.txt`、`opening_human.txt`、`report_human.txt`
- 附件筛选：`selector_system.txt`、`attachment_selector_human.txt`

### 2.4 结构化输出模型与校验机制
Excel 方向使用 `QueryRewriteResult`、`CaseExtractResult`、`LawQueryRewriteResult`、`MinimalCaseRow`；Word 方向使用 `OpeningContent`、`WordReportContent`、`AttachmentCaseSelection`。这些模型在字段层面定义了必填约束、长度约束与列表长度边界，确保模型返回值满足后续导出要求。  
在工程实践中，这类约束显著降低了“文本看似合理但程序无法消费”的概率，是本项目能够稳定输出文档的关键机制之一。

### 2.5 运行建议与调优思路
建议先用小样本（例如目标案例数 5~10）调试 Prompt 和模型兼容性，再扩大到业务规模。若出现结构化输出为空、字段缺失或格式不稳定，应优先从三方面排查：模型接口兼容参数、Prompt 约束强度、输入上下文完整性。对高频失败场景应配置显式兜底与重试策略，而不是仅靠重复调用碰运气。

## 3. 项目创作所用素材、接口、工具等

### 3.1 创作素材与验证依据
本项目的业务设计并非“先写代码再找场景”，而是基于需求文档、报告模板、样例结果和字段参考图逐步反推实现。需求文档用于定义目标能力与验收边界，报告模板与示例文档用于约束输出结构，样例表格用于校验字段完整性和可读性。这样做的好处是，系统输出天然贴近真实交付要求，而不是停留在技术演示层面。

#### 3.1.1 主要素材清单
- `RequirementsDocument.md`
- `需求.md`
- `项目需求评审与系统架构实施计划.md`
- `类案检索报告撰写要求.md`
- `附件示例.md`
- `类案检索报告模板.docx`
- `1-案例检索报告.docx`
- `1-案例检索报告(clean).docx`
- `1-相邻关系纠纷表格汇总.xls`
- `【裁判规则库】类案检索法律AI产品.pdf`
- `下载字段.jpg`

### 3.2 外部接口与能力来源
法律数据能力来自得理开放平台，通过 `deli_api` 进行统一封装。模型能力通过 `LLM_BASE_URL + LLM_API_KEY + LLM_MODEL` 接入，当前实际使用腾讯混元大模型 API。  
在接口层面，案例检索与法律检索分别承担“事实样本召回”和“规则依据补全”职责，二者配合实现从案例到规则的完整论证链路。

#### 3.2.1 法律检索接口（得理开放平台）
- 案例检索：`/api/qa/v3/search/queryListCase`
- 法律检索：`/api/qa/v3/search/queryListLaw`

### 3.3 开发工具链与交付资产
项目使用 Python 生态完成全链路开发，核心工具包括 FastAPI、Uvicorn、Streamlit、LangChain、httpx、openpyxl、python-docx。交付内容不仅是源码，也包括可运行 API、可视化页面、Prompt 资产和可直接提交的 Excel/Word 成果文件。  
在法律场景中，这种“系统 + 文档成果”双重交付方式更符合实际使用习惯，也更便于团队协同和专家复核。

### 3.4 合规边界与应用原则
本系统定位为法律辅助分析工具，输出不构成正式法律意见。建议在使用中保留人工复核环节，并在成果文档中明确数据来源、模型生成属性和时效性边界。对关键结论的最终采纳应由具备法律资质的人员完成，以满足专业审慎要求。
